# 基于论文依据的下一阶段功能计划

> 本计划承接 `docs/research_gap_analysis.md` 的差距结论，只规划后续功能，不包含本轮代码修改。

## 建设目标

下一阶段应把 EduMind 从“演示级教育智能体工作台”推进到“以真实用户画像为主线的个性化学习闭环”。核心主线是：

登录用户 `user_id` → 学生画像 → 学习路径 → 资源推荐/生成 → 课程知识库 RAG 答疑 → 测评与学习分析 → 教师诊断 → AI 内容审核 → 反馈更新画像。

## 优先级路线图

| 阶段 | 优先级 | 目标能力 | 论文依据 | 预计涉及模块 | 验收标准 |
|---|---|---|---|---|---|
| Phase 1 | P0 | 用户登录与 `user_id` 绑定 | `2402.01666v2.pdf`、肖君等在线学习者画像、`3766918.3766987.pdf` | 登录页、API 客户端、后端认证、用户模型、画像模型 | 学生登录后所有画像、路径、资源、测评、答疑日志都能归属到同一个 `user_id`；不同学生互不可见 |
| Phase 2 | P0 | 画像归属和画像驱动推荐闭环 | 师亚飞等学习画像路径推荐、刘昕等“一人一堂”、PLORS、本体推荐模型 | `StudentProfile`、`LearningPath`、`GeneratedResource`、路径/资源接口 | 同一课程下不同学生生成不同画像、路径和资源；推荐理由能引用画像字段和薄弱点 |
| Phase 3 | P1 | 统一课程知识库 RAG | KG-RAG、TutorLLM、NotebookLM RAG、RAG-PRISM | 知识库上传、向量检索、Tutor/RAG 接口、内容审核 | 所有答疑按 `course_id` 检索课程资料；答案必须包含引用、置信度、无法回答提示和引用覆盖信息 |
| Phase 4 | P1 | 多智能体真实工作流 | von Neumann MAS、LLM Agents for Education、PAPPL、VITA | Agent 图、AgentRun、资源生成、问答、诊断、审核 | 工作流包含 Profile/Path/Resource/QA/Diagnosis/Audit/Report 节点；每个节点输入输出可追踪；审核失败时资源不能发布 |
| Phase 5 | P1 | 教师学习分析与薄弱点诊断 | VITA、数智化个性化学习综述、Data-driven personalized teaching | 教师端、测评分析、事件日志、报告服务 | 教师可按课程/班级查看薄弱知识点 TOP、风险学生、干预建议和干预后的变化 |
| Phase 6 | P1 | 管理员 AI 内容审核与质量控制 | RAG 原创性评价、RAG-PRISM、教育 Agent 风险综述 | 内容审核接口、管理员审核页、资源模型、系统日志 | AI 生成资源进入待审核队列；管理员可通过/驳回；审核意见、风险标签、引用覆盖持久化 |

## 具体实施建议

### 1. 用户与画像基础设施（P0）

建议先做最小可用认证，不追求复杂权限体系：

| 工作项 | 建议做法 | 验收点 |
|---|---|---|
| 用户模型 | 新增 `User` 表，包含 `id`、`username`、`password_hash`、`role`、`display_name` | 后端能创建学生、教师、管理员 demo 账号 |
| 登录接口 | 新增 `/auth/login`、`/auth/me`，返回 token 与当前用户 | 前端刷新后仍能恢复当前用户 |
| API 用户上下文 | `api/client.ts` 自动附带 Authorization | 后端接口能通过依赖拿到 `current_user.id` |
| 画像归属 | `StudentProfile` 增加 `user_id`，默认查询当前用户画像 | 张三和李四登录后看到不同画像 |
| 教师授权 | 建立教师-课程或教师-班级关系 | 教师只能看到授权课程下学生画像 |

### 2. 画像驱动路径与资源闭环（P0）

论文依据强调画像不是静态表单，而是持续更新的学习状态。建议画像字段分三层：

| 层级 | 字段示例 | 来源 |
|---|---|---|
| 基础画像 | 年级/专业、课程、目标、偏好、基础水平 | 登录资料、对话画像 |
| 认知画像 | 知识点掌握度、薄弱点、误概念、最近测评表现 | 测验、答疑、资源完成 |
| 行为画像 | 学习时长、点击资源、答疑频次、完成率、复习间隔 | 事件日志 |

路径生成应从“直接生成三阶段文本”升级为“基于知识点状态的路径推荐”：

1. 从课程知识库或知识图谱获取知识点和先修关系。
2. 从画像获取薄弱点、目标和偏好。
3. 生成路径节点，并为每个节点保存推荐依据。
4. 测评或答疑暴露新薄弱点后触发路径调整。

资源推荐应增加元数据：

| 资源字段 | 用途 |
|---|---|
| `knowledge_points` | 与路径、薄弱点、RAG 引用关联 |
| `difficulty` | 支持分层推荐 |
| `resource_type` | 讲义、案例、练习、测验、思维导图 |
| `target_profile_tags` | 对应学习偏好、基础水平、目标 |
| `review_status` | 接入管理员审核 |
| `recommend_reason` | 支撑可解释推荐和答辩展示 |

### 3. 课程知识库 RAG 与知识图谱（P1）

当前已有课程资料上传、切片、检索和固定 JSON RAG。下一步建议合并两套问答入口：

| 工作项 | 建议做法 | 验收点 |
|---|---|---|
| 统一入口 | 保留一个课程问答接口，例如 `/tutor/ask` | 前端学生答疑只走一个接口 |
| 课程隔离 | 检索必须使用 `course_id` | 不同课程返回不同知识库引用 |
| 引用约束 | 答案必须返回 `citations`、`confidence`、`based_on_material` | 无引用时提示无法可靠回答 |
| 画像增强 | 检索时加入学生薄弱点、当前路径节点 | 同一问题对不同学生可给不同练习建议 |
| KG-RAG 扩展 | 抽取知识点、先修、包含、易错关系 | 回答能说明知识点关系和下一步学习节点 |

建议先做“可解释 RAG”，再做完整知识图谱。答辩中可以把 KG-RAG 作为下一阶段增强点，但需要避免把当前固定 JSON RAG 说成完整 KG-RAG。

### 4. 多智能体工作流（P1）

建议将 Agent 节点调整为以下结构：

| Agent | 职责 | 输入 | 输出 |
|---|---|---|---|
| ProfileAgent | 生成/更新学生画像 | 用户、课程、对话、行为日志 | 画像 JSON、风险标签 |
| PathAgent | 生成学习路径 | 画像、知识点、课程目标 | 路径节点、推荐依据 |
| ResourceAgent | 生成/推荐资源 | 路径节点、画像、知识库 | 资源草稿、资源元数据 |
| QAAgent | 课程知识库问答 | 问题、课程知识库、画像 | 答案、引用、置信度 |
| DiagnosisAgent | 学情诊断 | 测评、答疑、资源完成 | 薄弱点、误概念、干预建议 |
| AuditAgent | 内容审核 | AI 生成内容、引用、策略 | 审核状态、风险标签、修改建议 |
| ReportAgent | 生成报告 | 全部过程数据 | 学生/教师报告 |

验收重点不是节点名称，而是每个节点的输入输出可追踪、失败可恢复、人工审核可介入。

### 5. 教师学习分析（P1）

教师端应减少静态 fallback 依赖，逐步接入真实数据：

| 分析能力 | 数据来源 | 论文依据 |
|---|---|---|
| 薄弱知识点 TOP | 测评反馈、答疑问题、路径调整日志 | VITA、数智化个性化学习综述 |
| 风险学生识别 | 掌握度、低分、低活跃、重复误概念 | 在线学习者画像、Data-driven personalized teaching |
| 干预建议 | 薄弱点、资源完成、学习偏好 | 一人一堂、TutorLLM |
| 干预效果回收 | 干预后测评、答疑减少、路径完成率 | VITA formative assessment |

短期可以继续使用规则估计掌握度，但要修复分析接口返回结构，并在响应中标明数据来源：真实统计、规则估计或 demo fallback。

### 6. AI 内容审核（P0/P1）

内容审核是答辩中容易被问到的风险控制点，建议优先补齐持久化闭环：

| 工作项 | 建议做法 | 验收点 |
|---|---|---|
| 审核数据模型 | 新增 `ContentReview` 或给 `GeneratedResource` 增加审核字段 | 资源生成后有待审核状态 |
| 自动初审 | 调用现有 `content_review_service.check_content` | 返回风险等级、引用覆盖、建议 |
| 管理员操作 | 新增通过/驳回/退回重生成接口 | 前端操作会写入数据库 |
| Agent 接入 | `AuditAgent` 在工作流中阻断高风险内容 | 高风险资源不能进入学生端 |
| 审计日志 | 记录审核人、时间、意见、前后状态 | 管理员端可追踪 |

## 风险控制建议

1. 不要把当前角色选择页描述为真实登录系统；应表述为“演示入口，下一阶段接入用户认证”。
2. 不要把当前固定 JSON RAG 描述为完整 KG-RAG；应表述为“已有课程知识库问答雏形，后续增强为 KG-RAG”。
3. 不要把 `review_agent` 模板描述为实际审核 Agent；应明确当前审核是规则接口 + 管理端演示队列。
4. 论文方案可以写完整闭环，但实现说明要区分“已实现、部分实现、计划实现”。

## 推荐近期开发顺序

1. 用户登录与 `user_id`：所有个性化能力的根。
2. 画像 `user_id` 归属与接口过滤：解决多用户画像隔离。
3. 画像驱动路径和资源默认链路：让学生端不再手动选择 profile_id。
4. 内容审核持久化：补齐 AI 生成内容安全边界。
5. 统一课程 RAG：将固定 JSON RAG 和课程向量库问答合并。
6. Agent 增加 DiagnosisAgent 与 AuditAgent：让多智能体工作流真正承接论文设计。
